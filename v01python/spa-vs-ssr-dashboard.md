# SPA를 포기했을 때의 득과 실

> 대시보드의 80%는 SSR로 충분합니다.  
> 핵심 질문: *"5년 후에도 LLM과 함께 별 학습 없이 이 코드를 수정할 수 있는가?"*

---

## ✅ 얻는 것 (장점)

### 1. 인지 부하 급감

SPA에서 관리해야 할 복잡성이 절반 이상 사라집니다.

| SPA 필요 | SSR로 대체 |
|---|---|
| 번들러 (Vite, Webpack) | 불필요 |
| 클라이언트 라우팅 | FastAPI 라우터로 통합 |
| 서버 상태 (TanStack Query, SWR) | DB → 렌더로 단순화 |
| 클라이언트 상태 (Zustand, Redux) | 거의 불필요 |
| 인증 토큰 관리 | 세션 쿠키 한 줄 |
| CORS 설정 | 같은 도메인, 신경 불필요 |

---

### 2. 진실의 원천 단일화

SPA의 흔한 버그인 **"백엔드는 200인데 화면은 옛날 데이터"** 문제가 원천 차단됩니다.  
매 요청마다 `DB → HTML` 이므로 클라이언트 캐시와 서버 상태가 어긋날 일이 없습니다.

---

### 3. 기술 스택 수명 연장

| 기술 | 메이저 변경 주기 |
|---|---|
| React | 2~3년마다 패러다임 변화 |
| 상태관리 | 5년간 5번 교체 (Redux → Zustand → …) |
| 빌드 도구 | Webpack → Vite → Turbopack |
| **HTML / CSS / HTTP** | **30년째 하위 호환** |
| **HTMX** | **2020년 이후 의도적으로 변화 최소화** |

LLM 시대에는 **학습 데이터가 안정적으로 풍부한 기술**이 큰 무기입니다.

---

### 4. 첫 화면 로딩 속도

| 방식 | First Contentful Paint |
|---|---|
| SPA (React) | 1~3초 (JS 다운로드 → 파싱 → 실행 → API 호출 → 렌더) |
| SSR (FastAPI + Jinja2) | 100~300ms (HTML 즉시 표시) |

모바일, 저사양 PC, 사내 네트워크 환경에서 체감 차이가 뚜렷합니다.

---

### 5. 배포 단일화

```
SPA : 프론트(Vercel) + 백엔드(서버) + CORS + 환경변수 분리
SSR : FastAPI 서버 하나 → 끝
```

Docker 이미지 하나, nginx 하나, 도메인 하나로 운영 가능합니다.

---

### 6. 순수 HTML/CSS로 커버 가능한 범위 확대

JS 없이도 구현 가능한 기능이 크게 늘었습니다.

```html
<!-- 모달 -->
<dialog id="modal"><form method="dialog">...</form></dialog>
<button onclick="modal.showModal()">열기</button>

<!-- 아코디언 -->
<details>
  <summary>월별 매출 보기</summary>
  <div>...</div>
</details>

<!-- 드롭다운: Popover API (2024 표준화) -->
<!-- 다크모드: prefers-color-scheme + Tailwind dark: -->
<!-- 스티키 헤더: position: sticky -->
```

---

### 7. 디버깅 단순화

- **SPA**: 콘솔 + 네트워크 탭 + React DevTools + Redux DevTools + 소스맵…
- **SSR**: 브라우저 우클릭 → **페이지 소스 보기** → 끝

LLM에게 디버깅을 부탁할 때도 HTML 응답만 보여주면 됩니다.

---

### 8. 보안 표면적 축소

- Jinja2 자동 이스케이프로 XSS 위험 감소
- API 토큰을 클라이언트에 노출할 필요 없음 (HttpOnly 쿠키)
- API 엔드포인트를 외부에 공개할 필요 없음

---

## ❌ 잃는 것 (단점)

### 1. 즉각적인 인터랙션 (가장 큰 손실)

| | SPA | SSR + HTMX |
|---|---|---|
| 입력 반응 | 즉시 (네트워크 왕복 없음) | 50~200ms 지연 |
| 애니메이션 | 부드러운 드래그 | 제한적 |
| 필터 반응 | 0ms | 서버 왕복 필요 |

**치명적인 케이스**: 드래그 앤 드롭 순서 변경, 실시간 차트 줌/팬, 인라인 셀 편집, 복잡한 다중 필터

---

### 2. 오프라인 / 약한 네트워크 대응 불가

SPA는 한 번 로드 후 캐시로 동작하지만, SSR은 매 클릭마다 네트워크가 필요합니다.  
→ 현장(영업·물류·의료) 대시보드라면 SPA가 유리합니다.

---

### 3. 고급 인터랙티브 시각화 한계

D3.js, Recharts, Plotly, 커스텀 Canvas/WebGL 차트는 본질적으로 JS 기반입니다.  
HTMX만으로는 한계가 명확합니다.

> 단, **Chart.js / ApexCharts**는 `<script>` 한 줄로 SSR과 잘 어울립니다.

---

### 4. 실시간 업데이트의 어색함

- **SPA**: WebSocket → 상태 업데이트 → 자동 리렌더
- **SSR + HTMX**: SSE 또는 폴링으로 HTML 조각 교체  
  → 여러 위치 동시 업데이트가 까다로움

> `hx-trigger="every 5s"` 폴링으로 80%는 해결 가능합니다.

---

### 5. 복잡한 다단계 폼

단계별 데이터 유지, 실시간 미리보기, 의존성 필드 변경 등 상태가 많은 폼은 SPA가 압도적으로 유리합니다.

---

### 6. 모바일 앱 코드 공유 불가

React Native / Flutter 출시 계획이 있다면 결국 API가 필요합니다.  
→ 처음부터 SPA + REST/GraphQL 구성이 효율적입니다.

---

### 7. 프론트엔드 인력 채용 어려움

신입 프론트엔드 개발자 대부분이 React를 학습합니다.  
"Jinja2 + HTMX로 합시다"는 거부감을 줄 수 있습니다.  
→ 1인 또는 풀스택 팀이라면 무관합니다.

---

### 8. 페이지 전환 깜빡임

매번 전체 페이지를 새로 로드하면 시각적으로 거슬릴 수 있습니다.

> **해결책**: `hx-boost="true"` 또는 View Transitions API(Chrome 2024 안정화)로 상당 부분 해소됩니다.

```html
<body hx-boost="true">  <!-- 모든 링크가 SPA처럼 동작 -->
```

## 💡 현실적 권장: 하이브리드 전략

> **"기본은 SSR, 필요한 부분만 Island처럼 SPA"**

```
대부분의 페이지 (목록·상세·설정·보고서)
  → FastAPI + Jinja2 + HTMX

복잡한 단일 페이지 (인터랙티브 차트, 칸반 보드)
  → React / Vue / Svelte 컴포넌트만 부분 임베드
  → 또는 Alpine.js + Chart.js 조합
```

이는 **Astro의 Islands Architecture** 철학과 동일하며, 실제로 가장 합리적인 접근입니다.
